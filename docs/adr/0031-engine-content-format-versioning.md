# ADR-0031 — Versioning policy for authored engine content formats

- **Status:** Accepted
- **Date:** 2026-09-01
- **Relates to:** ADR-0028, ADR-0030, INV-070, INV-073, INV-081; ENG-120, ENG-121,
  ENG-123, ENG-130, ENG-198

## Context

Bhippi owns four hand-editable, AI-editable formats in addition to scenes:
`bhippi-hud@1`, `bhippi-material@1`, `bhippi-shader@1` and `bhippi-prefab@1`. They can
outlive an app install and may be reviewed or generated by tools. Treating a format marker
as decoration would allow a newer writer to silently damage an older project.

## Decision

All four formats use the same compatibility policy:

1. The integer after `@` is the major compatibility version. A reader accepts only majors it
   explicitly implements and returns a typed error naming the received and expected marker.
2. Adding an optional field with a deterministic default is backward-compatible within a
   major. Removing, renaming, changing meaning/range, or identifier semantics requires a new
   major.
3. Parsers validate the entire document before it enters a session. Writers emit deterministic
   JSON from Rust domain types; neither the webview nor an AI response writes these documents
   directly.
4. A legacy format is upgraded only by an explicit, tested migration that preserves the
   original until the new document validates. Opening a document never silently rewrites it.
5. Unknown fields are accepted only where the Rust type deliberately has a forward-compatible
   extension map. Elsewhere they are rejected so misspellings cannot masquerade as features.

## Evidence

The format suites round-trip canonical documents and reject unknown future markers:
`material::tests`, `prefab::tests`, `hud::tests`, and the shader tests in `material.rs`.
Scaffold output is produced by those same domain types and parsed again in scaffold tests.

## Consequences

- New formats must declare this policy or an ADR explaining why they differ.
- A major upgrade ships reader, migration, fixtures, and rollback behaviour together.
- AI repair receives the parser's typed error and must re-run the same parser; prompt wording
  is never a compatibility mechanism.

## Alternatives rejected

- **One ADR per JSON format.** The compatibility decision is identical and four copies drift.
- **Best-effort parsing.** It turns misspellings and future fields into silent data loss.
- **Webview migrations.** Document ownership and validation belong to Rust (INV-073).
